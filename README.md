# Thread Pool на Java

## Описание проекта

Реализован собственный пул потоков для высоконагруженного серверного приложения.  
Не использовался готовый `ThreadPoolExecutor`. Был написан
собственный механизм управления потоками, очередями задач, параметрами конфигурации, логированием и политикой отказа. 

Также реализованно:
- настраиваемые параметры пула;
- механизм отказа при перегрузке;
- распределение задач между несколькими очередями;
- подробное логирование;

---

## Цель

Разработать собственный пул потоков, который:
- управляет количеством рабочих потоков;
- принимает `Runnable` и `Callable`;
- распределяет задачи между несколькими очередями;
- умеет корректно завершать работу;
- поддерживает отказоустойчивое поведение при перегрузке;
- может использоваться как напрямую, так и совместно с `Future` / `CompletableFuture`.

---

## Требования и реализация

### 1. Параметры настройки пула

Пул должен поддерживать следующие параметры:
- `corePoolSize` — базовое количество потоков;
- `maxPoolSize` — максимальное количество потоков;
- `keepAliveTime` и `timeUnit` — время простоя потока до завершения;
- `queueSize` — ограничение на размер очереди;
- `minSpareThreads` — минимальное количество резервных свободных потоков.

В проекте все эти параметры поддерживаются в классе `CustomThreadPool`.

---

### 2. Обработка отказов

В данной реализации выбрана политика `CallerRuns`:
- если все очереди заполнены и новые рабочие потоки создать уже нельзя, задача выполняется в потоке, который 
  пытался ее отправить;
- это снижает скорость поступления новых задач и выполняет роль естественного backpressure;
- при этом задача не теряется.
- она проста в реализации;
- она безопаснее простого отбрасывания задач;
- она хорошо подходит для серверного сценария, где лучше замедлить отправителя, чем потерять работу.


---

### 3. Распределение задач между очередями

В текущем проекте используется:
- несколько очередей задач;
- распределение входящих задач по алгоритму **Round Robin**;
- попытка перенаправления задачи в другую очередь, если предпочтительная очередь заполнена;
- механизм **work stealing**: если закрепленная очередь рабочего потока пуста, поток может забрать задачу из другой очереди.

**Почему выбран Round Robin:**
- алгоритм простой и предсказуемый;
- нагрузка распределяется равномерно без дорогого анализа всех очередей;


**Почему добавлен work stealing:**
- он уменьшает простой потоков;
- повышает вероятность равномерной загрузки работников;
- снижает ситуацию, когда одна очередь перегружена, а другая пуста.

## Архитектура решения

Проект состоит из следующих основных компонентов:

### `CustomExecutor`
Интерфейс управления пулом.  
- `execute(Runnable command)`
- `<T> Future<T> submit(Callable<T> callable)`
- `shutdown()`
- `shutdownNow()`

В проекте интерфейс расширен дополнительными удобными методами.

### `CustomThreadPool`
Основная реализация пула потоков.  
Отвечает за:
- создание core- и extra-worker потоков;
- хранение и обработку очередей;
- прием новых задач;
- балансировку задач;
- учет состояния пула;
- запуск/остановку worker-потоков;
- корректное завершение работы.

### `NamedThreadFactory`
Кастомная фабрика потоков.  
- присваивать потокам уникальные имена;
- логировать создание и завершение потоков.

В проекте потоки получают имена вида:
- `MyPool-worker-1`
- `MyPool-worker-2`
- `StopPool-worker-1`
  и т.д.

### `RejectionPolicy` и `CallerRunsRejectionPolicy`
Инкапсулируют поведение при перегрузке пула.

### Worker
Рабочий поток, который:
- обслуживает закрепленную за ним очередь;
- выполняет задачи;
- может воровать задачи из других очередей;
- завершает работу по `keepAliveTime`, если поток не относится к обязательному ядру пула;
- прекращает работу при `shutdown` / `shutdownNow`.  
  
---

## Жизненный цикл пула

### Создание
При создании пула:
- создаются очереди задач;
- предварительно поднимаются core-worker потоки;
- каждый поток регистрируется через `ThreadFactory`.

### Прием задач
При поступлении задачи:
1. выбирается очередь по Round Robin;
2. если очередь заполнена, пул пытается положить задачу в другую очередь;
3. если свободных потоков становится меньше `minSpareThreads`, пул пытается создать дополнительный worker;
4. если задача все равно не может быть принята, применяется политика отказа.

### Выполнение задач
Каждый worker:
- берет задачу из своей очереди;
- при отсутствии задач пытается украсть задачу из других очередей;
- выполняет задачу;
- логирует ключевые события.

### Idle timeout
Если поток не относится к `corePoolSize` и простаивает дольше `keepAliveTime`, он завершает работу. 

### `shutdown()`
Метод `shutdown()` переводит пул в режим завершения:
- новые задачи больше не принимаются;
- уже поставленные задачи продолжают выполняться;
- после опустошения очередей worker-потоки завершаются.

### `shutdownNow()`
Метод `shutdownNow()`:
- запрещает прием новых задач;
- очищает очереди;
- прерывает активные worker-потоки;
- возвращает невыполненные задачи;
- уже исполняемые задачи завершаются через механизм `interrupt`, если задача корректно обрабатывает прерывание.

## Логирование

В проекте используется `SLF4J + Logback`.

Логируются следующие события:
- создание потока;
- запуск core / extra worker;
- постановка задачи в очередь;
- перенаправление в другую очередь;
- выполнение задачи worker-потоком;
- ситуация перегрузки;
- выполнение задачи в caller thread;
- запрос `shutdown`;
- запрос `shutdownNow`;
- остановка worker-потока;
- удаление worker из пула;
- прерывание long-running задач.

Примеры сообщений:
- `Created thread MyPool-worker-1`
- `Task accepted into queue 0`
- `Preferred queue 1 is full, task redirected to queue 0`
- `Pool overloaded. Running task in caller thread.`
- `Worker MyPool-worker-2 executes task`
- `Shutdown requested`
- `ShutdownNow requested`

## Критерии оценки производительности

Все значения в таблице получены экспериментально на одной машине, на JDK 17, после предварительного прогрева (warm-up). 
Для каждого сценария выполнялось несколько прогонов, в README приведены усредненные значения.

Сравнение проводилось между:
- собственным `CustomThreadPool`;
- стандартным `ThreadPoolExecutor` с максимально близкой конфигурацией.

### Методика

Использовались два сценария нагрузки:
1. **CPU-bound** — вычислительные задачи;
2. **Sleep/I/O-like** — задачи с ожиданием (`Thread.sleep(...)`), имитирующие I/O-задержки.

Во всех тестах замерялись:
- `total time, ms` — общее время выполнения набора задач;
- `throughput, tasks/s` — число выполненных задач в секунду;
- `avg latency, ms` — среднее время завершения одной задачи от момента отправки в пул;
- `p95 latency, ms` — 95-й перцентиль времени завершения.

### Результаты

| Сценарий | Пул | core/max | queueSize | tasks | total time, ms | throughput, tasks/s | avg latency, ms | p95 latency, ms |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| CPU-bound | CustomThreadPool | 4/8 | 1000 | 5000 | 28,93 | 173454,17 | 7,27 | 14,26 |
| CPU-bound | ThreadPoolExecutor | 4/8 | 1000 | 5000 | 21,85 | 228900,40 | 3,90 | 4,94 |
| Sleep/I/O-like | CustomThreadPool | 4/8 | 1000 | 1000 | 4751,86 | 216,34 | 1925,00 | 4419,39 |
| Sleep/I/O-like | ThreadPoolExecutor | 4/8 | 1000 | 1000 | 3892,09 | 256,93 | 1953,29 | 3703,46 |

### Вывод

По результатам измерений `ThreadPoolExecutor` оказался быстрее в обоих сценариях.

Для **CPU-bound** нагрузки стандартный пул показал:
- меньшее общее время выполнения (`21,85 ms` против `28,93 ms`);
- более высокий throughput (`228900,40 tasks/s` против `173454,17 tasks/s`);
- заметно меньшие задержки (`avg latency = 3,90 ms`, `p95 = 4,94 ms` против `7,27 ms` и `14,26 ms` у кастомного пула).

Для **Sleep/I/O-like** нагрузки стандартный пул также оказался эффективнее:
- меньшее общее время выполнения (`3892,09 ms` против `4751,86 ms`);
- более высокий throughput (`256,93 tasks/s` против `216,34 tasks/s`);
- лучший `p95 latency` (`3703,46 ms` против `4419,39 ms`).

При этом кастомный `CustomThreadPool` выполняет требования задания, демонстрирует корректную работу под перегрузкой, 
поддерживает несколько очередей, собственную политику отказа, `Round Robin`, `work stealing` и подробное логирование.

## Исследование параметров

Было проведено небольшое исследование влияния параметров пула на производительность.

### Исследуемые параметры

- `corePoolSize`
- `maxPoolSize`
- `queueSize`
- `keepAliveTime`
- `minSpareThreads`
- `queueCount`

### Таблица наблюдений

| Конфигурация | core | max | queueSize | keepAlive | minSpare | queues | total time, ms | throughput, tasks/s | Комментарий |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---|
| B | 4 | 8 | 1000 | 3 | 1 | 2 | 31,11 | 160727,26 | Сбалансированная конфигурация |
| C | 6 | 10 | 2000 | 5 | 2 | 4 | 25,56 | 195644,94 | Больше ресурсов, выше стоимость простоя |

### Выводы

По полученным результатам конфигурация **C** показала лучший throughput (`195644,94 tasks/s`) 
по сравнению с конфигурацией **B** (`160727,26 tasks/s`), а также меньшее общее время выполнения (`25,56 ms` против `31,11 ms`).

Это позволяет сделать следующие выводы:

- увеличение `corePoolSize` и `maxPoolSize` может повысить throughput;
- увеличение числа очередей и общего объема буферизации может уменьшить общее время выполнения;
- более “ресурсная” конфигурация работает быстрее, но повышает стоимость простоя и потенциальные накладные расходы;
- конфигурация **B** выглядит как более сбалансированный вариант для умеренной нагрузки;
- конфигурация **C** лучше подходит для сценариев, где приоритетом является максимальная пропускная способность.

Итог: если важен баланс между скоростью и потреблением ресурсов, разумнее выбирать конфигурацию типа **B**. 
Если приоритет — максимальный throughput, лучше показывает себя конфигурация типа **C**.
## Балансировка нагрузки

В пуле реализовано несколько очередей задач.

Механизм балансировки работает так:
1. При поступлении новой задачи выбирается предпочтительная очередь по алгоритму Round Robin.
2. Если выбранная очередь заполнена, пул пытается поместить задачу в следующую доступную очередь.
3. Если очереди заполнены, пул пытается создать дополнительный worker, если это допускает `maxPoolSize`.
4. Если и это невозможно, применяется политика отказа `CallerRuns`.
5. Если worker не находит задачу в своей очереди, он пытается украсть задачу из другой очереди (work stealing).

Такой подход обеспечивает:
- равномерное распределение новых задач;
- уменьшение простоя worker-потоков;
- более устойчивое поведение при неравномерной нагрузке.

## Shutdown Semantics

В проекте используются две разные стратегии завершения:

- `shutdown()` — плавное завершение: новые задачи больше не принимаются, но уже принятые задачи продолжают выполняться;
- `shutdownNow()` — экстренное завершение: очереди очищаются, активные worker-потоки прерываются, невыполненные задачи
   сохраняются отдельно и могут быть проанализированы.
Такое поведение выбрано осознанно и соответствует стандартной практике работы с пулами потоков в Java.

## Примечания к измерениям

Абсолютные значения производительности могут незначительно отличаться между запусками из-за особенностей планировщика 
ОС, JIT-компиляции JVM, фоновой нагрузки на систему и прочих факторов.  
Поэтому для анализа важнее сравнивать общую тенденцию и относительное отличие результатов между конфигурациями.
